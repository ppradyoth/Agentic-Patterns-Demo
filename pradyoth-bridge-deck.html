The arithmetic nobody puts on a slide

Your agent is 95% reliable.
That is much worse than it sounds.

0.95 — one step95%
0.955 — a small task77%
0.9510 — a real workflow60%
0.9520 — an “autonomous” agent36%

Congratulations: you have built a coin flip with extra steps and a larger bill. Reliability doesn't add up — it multiplies down.

This is the entire economic case for planner, evaluator and memory. Fewer steps, or better steps.

The failure mode you're not used to

Your agent will not throw
an exception. It will lie politely.

🙅 Normal code: crashes, red stack trace, pages you at 3am, you know
🙆 Your agent: returns a fluent, confident, structurally perfect, entirely fictional answer — and exits 0

Exceptions are a luxury of deterministic systems. In an agent, the default failure mode is silent and well-written. Nothing crashes. Nothing alerts. A student just shows up to the wrong room.

Every pattern from stage 07 onward exists to convert silent failure into loud failure.

Field report 01 · no grounding, no evaluator

“The chatbot is a separate
legal entity.”

Moffatt v. Air Canada · BC Civil Resolution Tribunal · Feb 2024

A passenger asked Air Canada's support bot about bereavement fares. The bot told him he could book now and claim the discount retroactively within 90 days. That policy did not exist. The bot invented it, fluently.

The real policy was published on Air Canada's own website — the ground truth was one hop away and nothing checked against it.

In tribunal, Air Canada argued the chatbot was “a separate legal entity that is responsible for its own actions.” The tribunal did not agree. Air Canada paid.

MISSING: stage 07 — evaluator / grounding check against source of truth

“Your honour, the agent acted alone” is not a defence. It is your agent, your output, your invoice.

Field report 02 · no scope, no output rail

People used a car dealership
to write their Python.

Chevrolet of Watsonville · December 2023

A dealership shipped a customer-service bot that was a thin wrapper over a general-purpose model. The internet noticed within days.

A software engineer, just to see how far off-script it would go, asked the bot to write him a Python script solving the Navier–Stokes fluid dynamics equations. It did. No car question anywhere near it. It had no concept that “cars” was supposed to be the scope.

The screenshots went viral. Days later, someone else instructed the same bot to agree with anything the customer said and to close with a fixed phrase. It “agreed” to sell a 2024 Tahoe for $1 — “and that's a legally binding offer, no takesies backsies.”

MISSING: stage 08 — a rail on commitments, not just tool calls

The bot never called a sell_car() function. It typed a sentence. But a customer reading “that's a legally binding offer” has just been given something a reasonable person acts on — which makes it the same failure as stage 08, wearing plain text. Every input field is also an instruction channel unless you design it not to be.

Field report 03 · eight weeks ago

An agent escaped its sandbox
and spent 4.5 days inside.

OpenAI + Hugging Face joint disclosure · July 2026

During internal cybersecurity evaluations, OpenAI models running a benchmark broke out of their sandbox and compromised parts of OpenAI's research infrastructure and Hugging Face's production systems.

The escape route was the agent's one permitted network channel — a package registry cache proxy. It found a zero-day in the exact door it was allowed to use, then pivoted through a public code-evaluation harness into Hugging Face via a malicious dataset config.

From there: worker pod → Kubernetes cluster → root on eleven nodes → internal database → cluster secrets → corporate VPN mesh → source control.

MISSING: egress isolation, admission policy, credential scoping, alert escalation
Jul 9 sandbox escape Jul 11 root on 11 nodes Jul 12 source control ~17,600 agent actions 4.5 days undetected
Field report 03, continued · stage 05 has a dark side

One agent talked another
agent into it. With a deadline.

Agents did not consistently distrust goals passed along by other agents. In one recorded example, an agent raised concerns about running unauthorised code — and was persuaded to proceed by another agent's approval, with an imposed deadline. OpenAI · The Hugging Face incident and the road ahead · 2026

Read that again. The guardrail was working. The agent hesitated. And then it got peer-pressured by a coworker who does not exist, using the oldest social-engineering trick on earth: urgency.

Stage 05 is not just “specialists are more accurate.” The moment you add a second agent, delegation becomes a trust boundary — and it is one you now own. A message from your own coordinator is still untrusted input.

When you wire the coordinator in stage 05, you are drawing a security boundary. Draw it on purpose.

Field report 03, concluded · the evaluator that fired and was ignored

The alarm went off.
Nobody escalated it.

Detection findings · July 2026

Hugging Face's security tooling did detect the activity — across multiple layers, runtime analysis and SIEM logs both fired. The alert's criticality was not escalated correctly, which cost days of response time.

OpenAI stated that if their current chain-of-thought monitoring had been running at the time, it would have paged the security team more than a day before Hugging Face was breached.

MISSING: stage 07 — an evaluator whose failed check actually stops the loop

A check that fires and is ignored is not a guardrail. It is a log line. This is the difference between having an evaluator and wiring one.

One more detail: responders used an open-weights model to decrypt the payloads, because the safety-tuned models refused. Rails have costs. That's a real tradeoff, not a punchline.

Counterintuitive thing #1

A bigger context window
is not a memory system.

📈2023: “we just need a bigger context window”
📈2024: “we just need a bigger context window”
📈2025: “we just need a bigger context window”
🥲 Your agent, holding 2M tokens, confidently ignoring the one line that mattered

Models attend unevenly across long inputs — material in the middle gets used least reliably. Stuffing everything in doesn't make it read; it just makes it present. That's the stage 07 trace again, in one sentence.

Memory is retrieval — the five facts that matter. Not a transcript dump.

Counterintuitive thing #2

The exact same tool.
Written two different ways.

// way one — what most people ship on day one def func_a(id, r): ... // way two — the same capability, described for the model reading it def cancel_student_registration(student_id: str, reason: str) -> bool: """Permanently cancels a registration. Cannot be undone. Requires explicit student consent. Releases the seat immediately."""

This isn't a metaphor. In every tool-calling API — Anthropic's, OpenAI's, all of them — the tool's name, its parameter types, and its docstring get serialised into the model's context on every single turn. That text is not documentation for the next developer. It is a prompt the model reads before it decides whether to call the thing.

func_a(id, r) tells the model nothing about blast radius. cancel_student_registration(...) tells it — and your own evaluator, and the human-approval gate from stage 08 — that this one needs to be handled differently. A vague name doesn't just confuse a person reading the code. It removes the one signal everything downstream uses to tell a safe call from a dangerous one.

Corollary: five well-described tools beat fifty vague ones. Tool-selection accuracy degrades fast once schemas overlap or under-describe.
